# Snapshot — frozen demo outputs

The markdown + JSON files in this directory are **byte-frozen** outputs
from a known-good ARIP run against the demo stack. They exist so that:

- Docs that link to a report (e.g. `pool_exhaustion-rca.md`) keep
  resolving even when nobody has run the demo recently.
- A pilot reviewer can read what ARIP *will* produce without spinning
  up Docker.
- Recording a video / screencast can reference fixed text rather than
  whatever output happens to land that day.

## What is and isn't stable across runs

| Element                       | Stable run-to-run?                                    |
|-------------------------------|-------------------------------------------------------|
| Report structure (sections)   | Yes — deterministic markdown writer                   |
| Primary hypothesis title      | Yes — derived from rule logic + telemetry shape       |
| Confidence value              | Yes (within ±0.02) — function of corroboration signals|
| Suggested next step text      | Yes — rule-template-driven                            |
| Per-attempt retry numbers     | Yes — payment-service's retry policy is fixed         |
| Trace IDs                     | **No** — generated by OTel SDK, random each run       |
| Order IDs                     | **No** — embed `Date.now()` from the Playwright test  |
| Timestamps                    | **No** — wall-clock when the failure occurred         |
| Span durations (microseconds) | **No** — machine load varies                          |
| Fingerprints                  | Yes — computed from rule_id + service set + evidence kinds |

The snapshot files were captured to demonstrate **what shape** of
output to expect, not to be reproduced byte-for-byte. When verifying
your own run against these, compare:

- Section presence (every snapshot section should appear)
- Rule firing (same primary rule_id per scenario)
- Confidence band (high / medium / low matches)
- Evidence kinds (same set, even if the specific IDs differ)

Do not compare specific span IDs, order IDs, timestamps, or
machine-time durations.

## Regenerate

```bash
cd <repo-root>
docker compose up -d --wait
bin/arip-e2e.sh
# Pick the freshest report per scenario:
cp reports/checkout-succeeds-without-exhausting-retries-*.md  docs/examples/retry_storm-rca.md
cp reports/checkout-latency-stays-within-sla-*.md             docs/examples/pool_exhaustion-rca.md
cp reports/order-transitions-stay-non-interleaved-*.md        docs/examples/concurrent_modification-rca.md
cp reports/checkout-returns-200-ok-fails-under-inventory-*.md docs/examples/downstream_error-rca.md
cp arip-pr-comment.md                                          docs/examples/pr-comment.md
```

The other three (`abstention.md`, `fingerprint-cross-run.md`,
`jaeger-trace-retry-storm.md`) are produced by small Python scripts
documented in [README.md](README.md) — they are non-trivial to
re-generate and should only be refreshed when the underlying schema
changes.

## Anti-drift

The
[arip-core/tests/test_calibration_benchmark.py](../../arip-core/tests/test_calibration_benchmark.py)
file enforces that the engine continues producing the same *shape* of
output under the same telemetry shape. If a refactor changes any
shipping fixture's primary rule, confidence band, or evidence-kind
set, that test fails — the snapshots here are downstream of that
guard.

In other words: the snapshots are illustrative, the unit tests are
canonical. Both should agree.
